# Discord OAuth web controls

The web UI uses Discord's authorization-code login flow with only `identify` to prove the controller's identity. The existing Discord connection separately verifies that user's roles in the active stream's guild. Web login does not replace the streaming account's `TOKEN`.

1. Create an application in the [Discord Developer Portal](https://discord.com/developers/applications).
2. Register the exact redirect URL ending in `/auth/callback`. Use HTTPS for remote access; local development can use `http://localhost:8080/auth/callback`.
3. Set `DISCORD_CLIENT_ID`, `DISCORD_CLIENT_SECRET`, and `DISCORD_REDIRECT_URI` in the server's private environment. Do not commit the secret.
4. Configure guild role/user grants using `PERMISSIONS_FILE`, then set `SERVER_ENABLED=true`. Unconfigured guilds allow only owners and Administrators.
5. Join a voice channel and request `!join` or `!stable`. Open its claim link, sign in as that command's author, and explicitly choose **Start my browser and stream** after reading the screen visibility notice.

Every stream requires the web server and complete OAuth configuration. `SERVER_ENABLED=false` or missing credentials prevents startup before Discord login; there is no anonymous fallback. A login alone grants no browser access: current guild, voice channel, active session, and role/user permissions are checked on every HTTP and Socket.IO action. Only the exact stream owner with current `join` permission can read metadata, navigate, send keys, search or use presets. Admin/control grants allow same-channel Discord `!leave` but do not share the owner's browser. The UI shows login, denied-access, and expiry messages.

OAuth state is cryptographically random, HMAC-signed, browser-bound, and short-lived. Abandoned login requests allocate no shared pending-login slots. Successful login states cannot be replayed; failed callbacks clear the browser cookie. A Discord account is limited to ten successful logins per five minutes and three concurrent sessions. At total session capacity, the oldest session is evicted instead of blocking new logins. Opaque session cookies are HttpOnly/SameSite=Lax, and Secure for HTTPS; OAuth bearer tokens are used only during the identity lookup and are not retained in web sessions; refresh tokens are not stored. State and sessions are discarded on restart. Sessions expire at the earlier of token expiry or eight hours; expiry requires a fresh login. Logout immediately disconnects that session's sockets.

REST writes require the session's CSRF token and exact public Origin. Socket.IO checks Origin on polling and WebSocket requests and validates the session/CSRF token on connection. Every event rechecks expiry, voice state, current session, and capabilities. Browser URL/preset updates are sent only to currently authorized logins of the owner. The existing Discord connection fetches fresh guild roles, with proof cached for at most 30 seconds and refreshes shared across browser sessions; role revocation can take that long, while voice/session changes apply on the next action. If verification is temporarily delayed, the server reports 503, disables controls, and the UI retries automatically. Expired role proof never extends access during a delay.

Native listening and Compose host publishing default to loopback. Keep the published port private behind an HTTPS reverse proxy; set the callback to its public origin. The container listens on `0.0.0.0` internally. HTTP(S) private media servers remain usable, but explicit `file:`, `javascript:`, `data:`, browser-internal URLs and URL credentials are rejected before Selenium.

A claim locator is not an ownership credential. GET and the OAuth callback only display/sign in; starting requires a same-origin POST with the login's CSRF token, the original author, current guild/voice/join verification and an unused, unexpired reservation. Claims expire after five minutes, deduplicate repeated requests without extending the deadline, and are cancelled by `!leave`, owner departure or restart. One POST atomically owns startup before any browser/voice/capture allocation. OAuth uses no guild scope and retains no bearer/refresh token.

Make the configured callback origin reachable by every prospective streamer. Remote users need the public HTTPS callback (for example `https://theatre.example/auth/callback`), rather than a localhost URL pointing at their own computer. Loopback HTTP remains available for local development. Compose retains loopback host publishing; expose remote access through the explicitly configured HTTPS proxy.

Automated tests use a stub OAuth provider and real HTTP/Socket.IO transports. Real Discord consent and a deployed callback require a configured application. See [Discord's OAuth documentation](https://discord.com/developers/docs/topics/oauth2) for the authorization-code grant and scopes.
